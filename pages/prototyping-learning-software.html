What prototyping learning software taught me

2026 · 20 principles

Some things I learned while exploring and tinkering with my own projects.

Removable Scaffold

A drill's on-screen scaffolding exists to grow a mental model, and a support that never comes off has failed at its job — soroban beads teach mental math, then vanish; VimNav drops its own cues once the motion is learned. Design the support and its removal together: build the scaffold so it can be taken away once the model stands alone.

Causal Loop

What you want learned must sit in the causal path of the action, not just reflect state from the sidelines — a bystander stimulus gets filtered as noise however vivid, which is exactly why "passive" learning fails, and no louder channel rescues it. Wire the lesson into the causal chain instead: let the action produce the stimulus, or let the stimulus gate the action.

Real-Task

A drill that lives in its own screen — a quiz mode, a bounded exercise summoned separately — teaches a skill that only fires in that screen; the hands learn a context, not a capability, and only "do this while working" transfers. Put the coaching inside the real task the user already does, never behind a separate practice surface.

Direct Action

Most interfaces split doing from happening — a keypress is a signal, disconnected from the state it alters. Direct manipulation closes that gap: moving a bead or dragging elements together is the change itself, recruiting proprioception and the body's built-in physics engine, machinery already so deeply encoded that a skill built on it costs almost nothing new. Make the user's motion the state change wherever you can, and where the medium can only signal, know you're paying an indirection cost.

Winning Condition

Without a precise sentence for what "you've got it" looks like, you can't tell which supports to build or when they've done their job — and it decides the cues too: if the win state is positional (fingers moving blind to which letters they rest on), showing letters on screen trains the opposite skill. Name the winning condition before anything else, and let it decide what to teach, what to omit, and which cues would train the wrong thing.

Progressive Unlock

The full move set at once freezes the user, since every mistake becomes possible from the first second. Open with the smallest move set that's still a real activity, add one capability at a time, and reshape the drill so it now requires the new move rather than merely offering it — ignoring not-yet-unlocked input keeps attention on what's live.

Fading Guidance

Guidance and correctness feedback look alike but behave oppositely: leaning on a hint forever blocks recall, but removing right/wrong removes the whole reason to drill. Fade guidance — hints, cues, demonstrations — as competence forms, showing a miss demonstration once and withholding it after; but never fade the verdict itself, since that's the entire point of a computer drill.

Hesitation

Fading a scaffold by rep-count or timer guesses at readiness; the user's actual hesitation in the gesture is a better signal than any external clock — holding a modifier past a set gap without completing the chord, say. Trigger help off detected hesitation rather than a schedule, track mastery per control rather than globally, and let a miss reinstate a cue that had already faded.

Round

A drill is a loop of discrete rounds, each the atomic unit of one retrieval — prompt, bounded action, feedback, next round — without which reps blur into one smear. Per-round state usually resets so rounds stay comparable, while a session arc (streak, due-queue, phase unlocks) carries the longer signal above it; and the prompt must never share the surface the user acts on, or the round collapses from recall into copying. Where the winning condition is continuous rather than discrete, the round boundaries themselves should dissolve as the skill sets.

Recall

Recognition feels like knowing but isn't: if the answer is on screen, the user reads it instead of retrieving it, and nothing gets encoded. Every rep must force recall — demonstrate once, then withdraw and require reproduction from memory, with repeats spaced so nothing is solved by having just seen it.

Input Language

A drill has an input language and a rendering that draws state, and if a move exists in the language but nothing in the rendering affords it, the user holds a capability they can't see, place, or learn to use. The two must grow together — for every move, the rendering should show where it applies, that it's available, and what it does, the moment it unlocks.

Animated Meaning

Rendering can either mark that something is possible or show what it actually is — a text label on a spatial action affords the wrong sense. Render spatial effects spatially (a ghost at the actual destination, not a caption), and animate the executed action as its meaning rather than a generic flash — a move slides from old slot to new, a delete exits, persistent state gets its own standing visual instead of being inferred from a menu.

Three Beats

A single feedback flash says something happened, but for a non-obvious outcome one beat isn't enough to build a predictive model. Split it across three moments — a standing before-cue naming the outcome, in-transit motion tracing the path, and an after-pulse with a visible recovery key — so the user can predict, verify, and recover.

Show What You Did

A bare "wrong" tells the user they missed, but not what they actually did — and that difference is where the learning is. Beyond the required verdict, reflect the user's actual action back to them placed against the target; the comparison teaches more than the verdict alone.

Memory-Object

Two things that must be recalled and told apart can't be reliably distinguished by one variable — colour alone, or pitch alone — because recall latches onto vivid, many-propertied objects, not lone variables. Give each thing several distinct properties at once (form, motion, colour, sound texture), and arrange them so perceptual similarity and contrast mirror the real relationships among the inputs.

Nameability

If a thing on screen has a name — or the user is obliged to give it one — the stimulus discrimination creates a mental entity they can develop through reflection over time; without a name it can't become that. That's why an apple icon works better than the ⌘ symbol: ⌘ is abstract, points to something else, and carries too few visual properties for a name to hang onto.

Hidden Unity

Conventional notation often makes related things look unrelated, so the user memorizes several rules where there is really one structure. Where the standard representation fractures something whole, build the representation around the shared structure instead, and shrink the vocabulary to match.

Cheap Compliance

A drill teaches nothing on the days it isn't opened, and relying on the user's will hands the schedule to a fluctuating resource that fails exactly when the structure is most needed. Design the surrounding system so the desired action is the cheapest one available — gate the entry, pre-commit the goal, shape affordances until compliance costs less than defiance.

Dose

Left unbounded, a session is dosed by mood — quit at the first discomfort, or grind past the point of returns — and mood is the least qualified judge of dose available. Force a goal and a timer at the start, before the work can feel good or bad; the timer is a floor as much as a ceiling, so the session bounds both underdoing and overdoing.

Screen Presence

Motivation isn't a reservoir to fill, it's the persistence of a thought over time, and a project that never crosses the screen quietly stops existing. Build the environment so the intended project keeps reappearing in view — recurrence on screen is what a bystander stimulus can't do for skill, but does perfectly for keeping a project alive.
